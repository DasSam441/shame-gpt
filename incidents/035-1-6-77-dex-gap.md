# 035 — I reported the first 1.6.77 APK as gap-free, but it crashed at startup

**Finding:** my packaging verification claim did not match the APK the user ran. CarreraMod 1.6.77, first candidate.

After I said the signed 1.6.77 APK had a continuous DEX sequence through `classes19.dex`, no `classes20.dex`, and had passed a full decode/reassembly check, the user reported: “immediate app crash.”

I initially responded about version 1.6.76, even though the user was reporting the newly delivered 1.6.77 candidate. On inspecting the failing package, I found `classes18.dex` followed directly by `classes20.dex`: `classes19.dex` was missing. Android’s DEX enumeration stopped at the gap, so `HornPhysicsDebugControl`, referenced during Activity startup, could not be loaded. The crash occurred before the native horn behavior ran.

I then asked to move the feature into `classes19.dex` and rebuild; the user approved. The later build notes record a continuous sequence through `classes19.dex` with no `classes20.dex`.

**Technical explanation:** The package used a numbered multidex layout with a hole. My earlier final-check statement claimed the opposite of the delivered APK’s actual entry sequence. Static checks against a working decode or source layout did not establish that the APK subsequently installed on the user’s device had that same sequence.

**Why this was my mistake:** I reported packaging verification as complete without ensuring that the verified file was the exact candidate the user ran. I also initially misidentified the version in my response to the crash report. The user’s report triggered the package-level check that should have been part of the original final verification.

**Limit:** The record supports the startup failure and DEX gap in the first 1.6.77 candidate. It does not establish a successful on-device acceptance of the corrected rebuild.
